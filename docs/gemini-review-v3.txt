『JEWEL RING / IMPLEMENTATION PLAN 03（第3版 2026年9月20日）』について、エンジニアリング（SwiftUI/Metal・グラフィックス・アーキテクチャ）、ゲームデザイン（収集・ミニゲームUX）、およびプロジェクト移行運用の観点から多角的にレビューを実施しました。

全体として、前版（H01〜H26）の決定事項との整合性を厳密に保ちつつ、実験的コードから製品品質への脱却に向けた技術的・運用的な論点が極めて高い解像度で整理されています。特に「ロジック（判定・成否・報酬）と演出（描画・破砕品質）の完全分離」**および**「外部境界（保存・将来同期）の先行抽象化」が徹底されている点は非常に堅牢です。

以下に、高評価できるポイント、実装時に特に注意・検討すべき技術的リスクと改善提案、および各セクションに対する詳細フィードバックをまとめます。

---

### 1. 総評・高く評価できる設計方針

1. **描画負荷とゲーム判定の決定論的切り離し（Decoupling）**
* Glass Breakにおいて、赤点の期限（1.5秒）の起点を「エンコード/生成時刻」ではなく「Drawable提示時刻（Presentation Time）」とし、フレーム落ちやCPU破片生成の遅延がプレイヤーの持ち時間に不利益を与えない設計になっている点が秀逸です。
* 適応品質（LOD/破片数削減）によってゲームの成功判定や報酬量が一切変動しない方針が徹底されています。


2. **PBR（通常描画）とRTの二重基準の解消**
* レイトレーシングを単なる「派手なエフェクト」として追加するのではなく、同一のシーン座標・投影・材質カタログ（`JewelOpticalProfile` / `JewelMeshProfile`）を共有させ、RT ON/OFFで位置・サイズが変化しないことを事前検証項目に挙げている点が極めて実践的です。
* 屈折率やBeer–Lambert則による吸収計算において、カメラズームによる見た目のサイズ変化で光路長・濃度が破綻しないよう実寸換算を固定化する配慮がなされています。


3. **安全な保存・移行設計（Save Schema v1 → v2）**
* UIからの直接JSON読み書きを排し、`PlayerRepository`を通じた原子的書き込み（atomic write + backup）を維持。
* 将来のサーバー同期を見据えつつも、今回のフェーズでは「実際の通信を行わない無接続・模擬実装」に留め、スコープの肥大化を防いでいます。

### 2. 重点的な技術課題・実装時の注意点（改善提案）

#### ① Glass Breakの提示同期（Drawable Presentation Timing）のプラットフォーム差異

* **課題:** 実機（CAMetalLayerの`addPresentedHandler`）とSimulatorでは提示タイミングの取得精度・挙動が大きく異なります。SimulatorではGPU完了通知（CommandBuffer completion）による近似となるため、タイミング同期ロジックにプラットフォーム分岐が必須となります。
* **提案:** `FramePresentationNotifier`プロトコルを定義し、実機用（Metal Presentation APIベース）と開発/Simulator用（DisplayLink + CommandBuffer完了ベース）の実装を完全にDI（依存性注入）できる設計にしておくことを推奨します。また、バックグラウンド遷移やダイアログ表示時の「時計停止」状態からの復帰時に、古い提示通知が遅延発火して即座に時間切れ判定とならないよう、セッションIDと状態（active/paused）によるガードを二重化してください。

#### ② 破砕生成の非同期パイプラインとリソース管理（CPU/GPU）

* **課題:** 最大800〜1600破片のボロノイ/ドロネー分割や亀裂トポロジー生成をバックグラウンドスレッドで行う際、急な退出（戻る操作）や連続タップによるタスクキャンセルが適切に行われないと、バックグラウンドでのCPU高負荷とメモリリークが発生します。
* **提案:**
1. `TaskPriority.userInitiated`のSwift Concurrency（または専用Serial Queue）で管理し、1セッションあたり1つのアクティブ生成タスクのみを許可。新しいセッションが開始された場合は即座に直前のタスクへ`.cancel()`を発行し、分割ループ内の各ステップで`Task.checkCancellation()`を挟むこと。
2. 生成完了後の頂点・インデックスバッファのGPUへの受け渡しは、Triple Buffering（リングバッファ）または共有ヒープを用い、描画中（In-flight）のバッファをCPU側から上書き・早期解放しない安全機構（`dispatch_semaphore`によるGPU完了同期）を組み込んでください。



#### ③ 2つのMTKView構成からシングルパス/統合描画への将来移行

* **課題:** 5.2節にある通り、現在「背景ガラス」と「マーカーUI（赤点・期限リング）」が別々のMTKViewで重ねられている場合、UIKit/SwiftUI層でのコンポジットオーバーヘッドや、アルファブレンドの二重適用（ガンマ空間・線形空間の不一致による黒ずみ・白飛び）が発生しやすくなります。
* **提案:** ターゲットの半透明描画（光膜・光輪・期限リング）は、最終的なポストプロセスパス（または同一MTKView内の最終レンダーパス）へ統合することを中長期の推奨とします。当面別Viewを維持する場合でも、上層のMTKViewの`layer.isOpaque = false`、`clearColor = MTLClearColorMake(0, 0, 0, 0)`、およびブレンド係数（Premultiplied Alpha）を厳密に統一する必要があります。

#### ④ 収集枠（RingSlotPresentation）のヒットテストと操作性

* **課題:** 12スロットの円環配置において、スマートフォンの画面サイズによっては未所持の空き石座と隣接する所持宝石のタップ判定が重複・誤認識しやすくなります。
* **提案:** 単純なバウンディングボックス判定ではなく、画面中心からの極座標（角度θと半径r）による判定、もしくは「最もタッチ位置に近いスロットの中心からのユークリッド距離」を求め、最小タッチターゲット（44×44pt以上）を確保しつつデッドゾーンを設けるアルゴリズムの採用を推奨します。

### 4. 判断表（jewel-decisions-v3.xlsx）記入に向けた推奨方針の整理

計画書同梱の判断表（R01〜R28）について、開発着手前に回答すべき「先行判断」の推奨スタンスは以下の通りです：

* **R01〜R03（光学・RT）:** 物理ベースの写実性＋ゲームとしての視認性（内部反射の強調）。RTは対応実機のみON、詳細観察から適用。非対応端末ではグレーアウト＆明快な理由提示。
* **R04（環境）:** iOS 17（Metal 3ベース）をベースラインとし、Metal 4は対応OS/ハードウェア検出時のみオプトイン。
* **R06〜R08（空き枠UX）:** 空き石座＋獲得先明記。タップ時は直接ゲーム起動ではなく、確認小パネル経由（誤タップ防止）。
* **R09〜R11（Glass Break）:** 3秒予告での自動開始。赤点はSDFを用いた半透明光輪＋期限リング。
* **R12（名称）:** 画面表示は「Glass Break」「Glass Trace」へ統一し、コード/JSONキーの互換性（`grassBreak`等）は内部で維持。
* **R16〜R18（リポジトリ）:** 新規Privateリポジトリ新設。既存のBundle ID・署名を維持してローカルセーブの連続性を保証。
* **R27（開発順序）:** 「依存整理」→「空き枠・自動開始」→「PBR/半透明赤点」→「適応品質」→「RT」→「保存移行」の順序で進行。

本計画書は、設計の粒度・論理展開・リスク対策のいずれにおいても非常に完成度が高く、このまま工程0および先行判断（R01〜）の確定へ移行して問題ありません。
